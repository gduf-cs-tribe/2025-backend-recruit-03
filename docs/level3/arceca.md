# 第三轮后端考核说明(热重载技术方向)

## 失落世界的重编排

在那片由光芒与残响构成的世界里，Arcaea 并不只是乐曲。  
每一段旋律、每一块碎片、每一名搭档的状态，都会被记录在一座持续运转的“记忆中枢”中。

平时，这座中枢只负责向外界提供稳定的数据：  
当前开放的曲目、搭档的能力参数、活动的倍率配置，以及异象发生时应当遵循的解析规则。

但这一次，问题出现了。

一场新的异象正在扩散。  
光希望尽快修正错误的参数，让世界重新回到稳定的轨道；  
对立则指出，真正出问题的不只是参数本身，而是那套早已过时的规则逻辑。  
更麻烦的是，这座中枢已经承载着大量正在进行的连接，**一旦停机，正在收集记忆的人就会被强行中断。**

也就是说：

- 你不能直接停止服务；
- 你不能简单地重启进程；
- 你必须让这座“记忆中枢”在**持续运行**的情况下完成更新。

你的任务，就是为它实现热重载能力。

## 实现等级

### Level 1：光之调律（配置文件重载）

光提出的要求很直接：

> “有些事情，不需要改写世界本身。  
> 只要把参数调回正确的位置，旋律就会重新对齐。”

因此，在这一关中，你需要让服务支持**配置文件热重载**。

当配置文件发生变化时，服务应当能够在**不中断主进程**的前提下重新读取配置，并让新的配置立即对后续请求生效。

这一层中，可能被修改的内容包括但不限于：

- 曲目或活动相关的配置项；
- 搭档的数值参数；
- 奖励、倍率、开关等运行参数。

你需要证明：  
**配置变了，服务的行为也随之改变；但服务本身没有被重启。**

### Level 2：对立之重编（业务逻辑重载）

对立提出了更进一步的要求：

> “如果连规则本身都是错的，  
> 只修参数，不过是在给旧世界缝补裂痕而已。”

因此，在这一关中，你需要让服务支持**业务逻辑热重载**。

也就是说，不只是读取新的配置，  
而是当某个业务逻辑模块被修改后，服务能够在**不中断、不重启**的情况下，加载新的逻辑，并将其应用到后续请求之中。

这一层考察的，不再是“换一组数字”，而是：

- 更换一段处理规则；
- 修改请求的判定逻辑；
- 调整某个核心业务模块的行为。

你需要证明：  
**逻辑已经发生变化，但承载这一切的主服务进程始终还在原地继续运行。**

无论你决定先回应光，还是先回应对立，记忆中枢都只接受同一种修复方式：

- 你可以只完成 **配置文件重载**，也可以直接挑战 **业务逻辑重载**；
- 但无论选择哪一条路，都不允许通过重启服务进程完成更新；
- 也不允许通过重新拉起新实例替换旧实例，来假装世界从未中断；
- 更新后的配置或逻辑，必须真实作用于后续请求；
- 而在整个切换过程中，服务应尽可能保持可用。

## 考核任务概述

请实现一个具备**热重载能力的程序**，用以模拟"记忆中枢"在不停机情况下完成更新的过程。

程序形态不限，可以是 HTTP 后端服务、GUI 桌面应用、命令行工具或其他任何形式，只要能清晰演示热重载的效果即可。

热重载能力的验证方式：

- 程序在运行期间，修改配置文件或业务逻辑模块；
- 程序的行为（响应、界面、输出等）应反映出新的配置或逻辑；
- 全程不允许重启进程，不允许以拉起新实例替代旧实例的方式假装"热重载"。

请根据自己的能力与时间，选择完成以下任意一个等级：

| 等级 | 目标 | 简述 |
| --- | --- | --- |
| Level 1 | 配置文件热重载 | 服务运行时读取新配置，后续请求行为随之改变 |
| Level 2 | 业务逻辑热重载 | 服务运行时替换处理逻辑模块，后续请求由新逻辑处理 |

完成 Level 2 默认视为同时完成 Level 1。

## 技术与工程要求

### 1. 通用要求

- 统一的响应格式与异常处理
- 清晰的分层与模块划分（禁止所有逻辑堆在一层）
- 热重载过程中若新配置/逻辑加载失败，服务必须维持上一版可用状态，不得崩溃或进入不可用状态
- 支持多次反复重载，而无明显资源泄露（内存持续增长、旧模块残留、文件句柄未释放等均视为不合格）

### 2. 代码规范

- 使用 UTF-8 编码
- 使用符合语言规范的命名方式
- 严禁使用拼音或无语义命名
- 代码中每一个函数类都需要写明清晰的函数文档（注意函数文档和代码注释的区别）

### 3. Git 与工程管理

- 必须使用 Git 进行版本控制
- 仓库需为 **公开仓库（不限制 Git 托管平台，比如 GitHub / Gitee）**
- 需要：
  - 合理的 commit 粒度
  - 规范的 commit message

- 鼓励使用 Github Project 或 Readme.md 中的一些章节记录设计、问题与计划（非强制，我个人不喜欢用 issue 记录开发计划，Github Project 对于进度管理来说更加规范）

## 提示

在失落的世界里，记忆不会等待服务重启。  
无论是光试图修正的“参数”，还是对立试图改写的“规则”，  
它们都必须在旋律仍在继续的时候完成切换。

如果你一时不知道该从哪里下手，以下这些碎片也许能帮你确认方向：

1. 配置文件重载与业务逻辑重载并不是同一件事。  
   如果你的方案只能重新读取数值，却不能替换处理请求时真正执行的逻辑，那么它还停留在 Level 1。

2. “加载新内容”通常不是真正困难的部分。  
   更麻烦的是：旧内容是否还活着。旧模块留下的对象、缓存、定时器、文件句柄、监听器，甚至只是某个仍被引用的闭包，都可能让上一版逻辑继续滞留在内存里。

3. 如果你打算多次重载，请考虑资源回收问题。  
   一次成功的更新并不代表方案可靠；能否在多次重载之后依然保持稳定，往往比第一次加载成功更重要。

4. 一个可用的热重载方案通常不只需要“切换”，还需要“失败时不把世界一起带走”。  
   当新的配置或逻辑加载失败时，服务至少应当还能维持上一版可用状态。

毕竟，真正的异象从来不会等你发版。
